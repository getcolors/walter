Walter

One Google Cloud development machine, with reproducible tooling and private user environments.

  • Python controller
  • Google Cloud
  • Pinned SSH trust
  • Explicit recovery checkpoints

Introduction

Walter turns colors.yml into a development machine using PocketDeploy for cloud resources, local state, SSH authority and recovery. Python provisions the machine and each user environment. Nix, asdf, Git, OpenSSH and tool installers remain external tools.

The new deployment profile is walter-gcp. Existing deployments retain their independent state. Walter does not import legacy state or adopt resources by name.

Quick start

Install uv, OpenSSH, Google Cloud CLI and GitHub CLI. Authenticate Google Application Default Credentials for the configured project and sign into gh as the configured github-account. From the source checkout:

uv sync --locked --extra test
uv run walter --help
uv run walter init
uv run walter plan
uv run walter vault-save
uv run walter converge --verbose
uv run walter vault-save
uv run walter status
uv run walter ssh
uv run walter ssh --user rose

The portable walter launcher uses a pinned Python package. Configuration defaults to colors.yml in the caller’s directory; select another deployment with -f /absolute/path/colors.yml.

Review the planplan and converge --dry-run read cloud resources without provisioning or creating local SSH authority. They describe infrastructure changes and intended user reconciliation, not every package-manager action.

Configuration

Keep useful Walter google-* and tooling settings in colors.yml; Walter maps infrastructure settings into PocketDeploy internally. provider-compute: google selects the only supported cloud.

AreaSettings
Deploymentprofile, users, compute-prevent-destroy
Google Cloudgoogle-project, google-zone, google-machine-type, image and boot-disk settings
NetworkExisting google-network and google-subnet; walter-ssh-sources controls the owned SSH firewall rule
Toolingnix-packages, asdf-tools, corepack-packages, agent-tools, login-shell
Personal setupGitHub identity, repositories, Emacs, dotfiles-checkout, Atuin and optional agent credential seeding
Recoveryvault-id and vault-command

Resource names use <profile>-<component>-<purpose>, omitting redundant components. Immutable provider IDs and ownership labels establish authority. Walter owns its VM, boot disk and firewall rules, not the referenced network or subnet. Its HTTP/HTTPS firewall rule is disabled; inherited network rules still apply.

N4A uses ARM64 Ubuntu, Hyperdisk Balanced and gVNIC. C4A -lssd shapes require their fixed Local SSD count. Opt into local-ssd-scratch for disposable caches and build output; keep source, credentials and other durable work on persistent storage.

See the README and example configuration for details.

Development environments

Convergence follows preflight → local keys → compute → verified host trust → remote Python provisioning → local aliases. Machine setup runs with privilege; per-user installers permanently drop privilege before running.

Walter installs Docker for the primary login, Nix packages, asdf runtimes, Corepack and selected standalone agents. Every configured seat receives its own home and tooling. Exact asdf versions resolve once per invocation, including latest, and are shared across seats.

Repository setup uses the configured GitHub identity over HTTPS. Dotfiles use a small Python renderer for the checkout’s Ubuntu profile and preserve existing home files and later edits. Existing remote agent credentials are preserved. Emacs package warming runs asynchronously; inspect ~/.local/state/walter/emacs-packages.log for completion.

Credentials and access

Every variable assigned in .envrc.private must begin with COLORS_PAR_. Keep this file private and ignored. Load settings in your trusted shell; Walter validates assignment names but never sources the file. Never put secrets in YAML, command arguments or Git. Profile overrides still have to match recorded state identity.

Atuin requires COLORS_PAR_ATUIN_PASSWORD and COLORS_PAR_ATUIN_KEY. Google and GitHub use their CLI credential stores; VaultContext uses an authenticated, unlocked client session.

GitHub tokens and optional individual agent credential files travel through SSH stdin, not command arguments or SQLite. Walter never forwards an SSH agent. Host trust is verified before application credentials are sent.

Seats have private homes and no sudo or Docker-group membership. They share configured service identities and host networking; the primary login remains privileged. One local controller at a time operates the deployment’s .colors.sqlite journal and .ssh/ authority.

Recovery and deletion

Save a checkpoint before provisioning and after mutations. vault-save backs up local private bindings, SSH authority, known hosts and SQLite. It does not back up remote home directories or the boot volume; preserve remote work separately.

walter vault-restore --document DOCUMENT --version VERSION \
  --destination /absolute/recovery/directory

Place matching Git configuration in the destination first. Restore never deploys resources or sources private settings. Review plan before takeover. Missing state or SSH authority requires recovery; do not bypass host-key checks or replace identities to force access.

Deletion destroys remote workDeletion requires compute-prevent-destroy: false. Review delete --dry-run first. Deletion removes owned compute, boot storage, firewall rules and local SSH keys/aliases while retaining the SQLite receipt, configuration and Vault history. Local recovery checkpoints do not contain remote work.
